# Level 4 — Guided Training Parts B and C

Level 4 is complete for the frontend scope described below.

Level 4 completes Part A to Part B to Part C navigation and activates `/training/guided/part-b` and `/training/guided/part-c`. Part B and Part C require the established `run_id` and `attempt_id` search parameters. The page loads the existing ML attempt detail query and enables Part B only after Part A is completed; Part C requires completed Part B. Completed stages are immutable in the UI. Backend Run Management remains authoritative for conflicts and retries.

Part B posts to `POST /api/v1/preprocessing/run` through `mlClient` with `{run_id, attempt_id, preprocessing}`. The request types and default values mirror `ML_backend/app/schemas/preprocessing/preprocessing.py` and `defaults.py`. Basic controls expose method/direction-dependent outlier settings, missing percentage, Phase 4 enabled, and intermediate output selection. Advanced controls include value bounds/tolerance, fixed timeline correction, the built-in/custom gap mode, and Phase 1–3 values. Built-in gap mode omits `gap_profile`; custom mode sends all five ranges.

Part C posts to `POST /api/v1/feature-engineering/run` through `mlClient`. The default XGBoost and Isolation Forest choices send `model_type_hint` and omit `feature_engineering`, allowing backend-owned profiles to resolve their schema defaults. An optional profile editor sends a `feature_engineering` configuration with `default_profile` and the schema-supported `default_features` fields. Custom mode uses field-level editors for all 14 backend discriminators: `current_value`, `lag`, `rolling`, `time_bucket`, `time_cyclic`, `calendar`, `difference`, `percentage_change`, `seasonal_difference`, `rolling_zscore`, `ewma`, `rolling_slope`, `baseline`, and `residual`. Type changes start with a clean type-specific configuration; feature cards can be reordered, collapsed, and removed.

Reusable editors provide repeatable numeric/status lists, raw-value point cleaning, corrected-history settings, and the weighted-seasonal baseline shared by baseline and residual requests. Corrected-history source omits incompatible point-cleaning configuration. The backend-only `adjust=false` and `include_baseline_column=true` literals are shown as read-only information. Corrected-history minute divisibility and duration-to-point resolution require the resolved Part A bucket and remain backend-authoritative. Custom mode requires at least one feature; list, source, cleaning, baseline, and top-level settings are validated before submission. Default profile customization exposes the backend's XGBoost and Isolation Forest default-profile fields.

Both endpoints use the existing configurable synchronous workflow timeout. After responses or errors that may persist state, run, attempt, summary, and corresponding stage-report query keys are invalidated using the existing factories. HTTP failures retain status/error code and safe messages; successful HTTP responses are checked for the requested stage and workflow status. Part D remains disabled and is deferred to Level 5. The active Part C page uses field-level editors; the unreachable Part C JSON editor branch was removed from the former shared page, which now handles Part B only.

## Navigation and lifecycle

/training/guided and /training/guided/part-a open Part A. A completed Part A response with a completed Part A execution and returned identifiers exposes **Continue to Part B**. A completed Part B response exposes **Continue to Part C**. Both links use returned run_id and attempt_id URL parameters. A failed or incomplete response does not by itself unlock a next stage.

The Part A workspace saves returned identifiers in its URL and loads attempt detail when both are present. Part B and Part C also load attempt detail on direct entry or refresh. Persisted backend stage statuses restore eligible navigation without the original POST result. The stage indicator shows completed and current stages, links eligible steps, explains prerequisites, and keeps Part D disabled. Part B requires completed Part A; Part C requires completed Part B. Completed stages cannot be resubmitted. The attempt detail page offers one continuation action based on its stage lifecycle. For an incomplete or failed Part A it opens the Part A workspace to review target-attempt options; backend Run Management decides retry eligibility.

Every Part A, B, and C response, including HTTP-success workflow failures, invalidates the runs list, run detail, attempt detail, reporting run summary, reporting attempt summary, and corresponding stage report through existing query-key factories. Errors that may have persisted state invalidate the same keys for known identifiers. HTTP 409 lifecycle conflicts, HTTP 422 validation errors, network failures, and timeouts are shown as safe errors. Submission is disabled while synchronous execution is pending. Returned run, attempt, and completed-stage report links are available with the response; a report may remain unavailable until reporting has indexed it.
